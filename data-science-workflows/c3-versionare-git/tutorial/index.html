Cursul 3 · Manual

Versionare și colaborare cu Git

Același drum ca la curs, explicat pe larg și cu aceleași exerciții. Dacă le-ai făcut la clasă, apar deja rezolvate; dacă vrei să le reiei, îți poți reseta progresul din contul tău.

01 · Cursul

Versionare și colaborare cu Git

Ora de azi are două jumătăți care par fără legătură, dar nu sunt. În prima învățăm Git, adică felul în care un proiect își ține minte propria istorie. În a doua punem întrebarea de cercetare a proiectului vostru.

Legătura dintre ele e asta: un proiect de analiză nu e o grămadă de fișiere, e un drum. Git păstrează drumul, iar cadrul teoretic spune încotro duce. Fără primul, nu poți arăta cum ai ajuns; fără al doilea, nu poți spune de ce ai pornit.

02 · Cursul

De la cursul trecut

  • un script care cere date de la un API
  • un fișier în date/brute/
  • amândouă, deocamdată, doar pe laptopul tău

Exact asta reparăm azi.

Ce se întâmplă cu munca de săptămâna trecută dacă îți moare laptopul în seara asta?

Se pierde. Un fișier salvat pe disc e într-un singur loc. Git nu rezolvă singur asta: Git ține istoria local. Abia când o împingi pe GitHub există în două locuri.

03 · Ce face Git

Ce face Git

Un sistem de versionare rezolvă o problemă pe care toată lumea a avut-o înainte să știe că are un nume: fișiere numite analiza_final_v2_FINAL_bun.py, și nimeni care să-și amintească ce era diferit în v1.

ExploratorȘase lucruri
Distincția care se uită cel mai des

Git și GitHub nu sunt același lucru. Git e programul de pe calculatorul tău, care ține istoria. GitHub e un site care găzduiește copii ale acelei istorii. Poți folosi Git fără GitHub toată viața; invers, nu.

04 · Ce face Git

Cele trei zone

Ăsta e modelul mental fără de care Git pare un set de incantații. Nu e în prezentarea de la curs, dar fără el comenzile se învață pe de rost și se uită până săptămâna viitoare.

Mută tuMută-le tu
ZonaCe e acoloCum ajunge mai departe
Dosarul de lucrufișierele pe care le editezigit add
Zona de pregătirece ai ales pentru următorul commitgit commit
Istoricul localcommit-urile tale, pe laptopgit push

Zona de pregătire pare un pas în plus, inutil. Rostul ei e să poți face un commit cu trei din cele șapte fișiere pe care le-ai atins, pentru că numai alea trei țin de aceeași schimbare.

05 · Ce face Git

Git sau GitHub

Ești în tren, fără internet. Ce poți face?

Tot ce ține de istoricul local. Internetul îți trebuie abia la push și pull, adică exact la cele două comenzi care vorbesc cu GitHub.

Unde stă istoria proiectului tău, pe laptop?

În .git. Dacă ștergi dosarul ăla, ștergi istoria și rămâi cu fișierele așa cum sunt acum. Dacă copiezi tot dosarul proiectului pe un stick, copiezi și istoria.

06 · Primii pași

Repository

Un depozit (repository, sau pe scurt repo) e un dosar obișnuit, în care Git a făcut un subdosar ascuns, .git. Acolo ține toată istoria.

# porneste urmarirea

# prima intrebare, mereu: unde sunt?

Greșeala de început

git init dat din greșeală în dosarul tău de acasă pune sub urmărire tot ce ai pe calculator. Dacă ți se întâmplă, ștergi dosarul .git de acolo și nu s-a pierdut nimic.

Ce face git init?

Pornește urmărirea dosarului în care ești.

07 · Primii pași

Credențiale

Git scrie în fiecare commit cine l-a făcut. Nu verifică nimic: scrie ce i-ai spus. De aceea, dacă pui o adresă greșită, commit-urile tale apar pe GitHub ca ale nimănui.

Scrii codSpune-i lui Git cine ești
08 · Primii pași

Ciclul de lucru

În practică, o zi de lucru arată așa:

# unde sunt?
git status

# aleg ce intra in commit-ul asta
git add colectare/banca_mondiala.py

# il scriu in istoric, cu un mesaj care spune ceva
git commit -m "colectare de la Banca Mondiala, cu paginare"

# il trimit colegilor
git push
Cât de des faci commit

Mai des decât crezi. Un commit nu e o livrare, e un punct la care te poți întoarce. Regula practică: de fiecare dată când ai terminat un lucru care are un nume.

09 · Primii pași

.gitignore

Un fișier text, în rădăcina proiectului, cu ce nu trebuie urmărit:

# mediul virtual: se reface din requirements.txt
venv/
.venv/

# secrete: niciodata, in niciun fel
.env
*.key

# date mari: se aduc cu scriptul de colectare
date/brute/*.csv
!date/brute/mic_exemplu.csv

# gunoiul uneltelor
__pycache__/
.ipynb_checkpoints/
.DS_Store

Semnul exclamării face o excepție: linia de mai sus exclude toate fișierele CSV din date/brute/, iar cea cu ! lasă totuși unul mic, de exemplu, ca să poată rula cineva codul fără să colecteze tot.

10 · GitHub

GitHub

  • o platformă online care găzduiește depozite Git
  • un loc unde proiectul există și dacă laptopul nu mai există
  • locul unde echipa se întâlnește, fără să-și trimită arhive pe mail
  • un portofoliu: se vede cine ce a făcut, și când
Pentru voi, concret

Nota de la proiect se dă pe ce se vede în depozit. Nu pe fișierul final, ci pe drum: ce ați încercat, ce ați aruncat, cine a lucrat. Un depozit cu un singur commit în ziua predării spune o poveste, și nu una bună.

11 · GitHub

Ai deja un depozit local

Faci unul gol pe GitHub, fără README, și le legi:

Scrii codLeagă-l de GitHub

Nu ai depozit local

Atunci e și mai simplu: îl faci pe GitHub și îl aduci la tine.

git clone https://github.com/echipa/proiect.git

Clonarea aduce și fișierele, și toată istoria, și leagă singură origin.

12 · GitHub

De la dosar gol la depozit de echipă

ExercițiuPune pașii în ordine

De ce se creează depozitul de pe GitHub gol, fără README?

Pentru că un README creat pe GitHub e un commit pe care depozitul tău local nu-l are. La primul push, Git refuză, și primești un mesaj despre istorii fără legătură. Se rezolvă, dar e un sfert de oră pierdut la prima oră de Git.

13 · GitHub

Ce s-a întâmplat de fapt

Ai făcut git commit dar nu git push. Ce vede colegul tău?

Nimic. commit scrie în istoricul tău local. Până la push, munca ta există într-un singur loc, iar asta e exact situația de la începutul orei.

14 · În echipă

Ramuri

O ramură e o linie de lucru paralelă. Pe ea strici ce vrei, iar main rămâne întreg și gata de predat oricând.

Desenează tuDesenează-l tu
ComandaCe face
git branchce ramuri există și pe care ești
git switch -c curatarefaci una nouă și treci pe ea
git switch mainte întorci
git merge curatareaduci în main ce ai făcut pe ea
De ce nu lucrează toți direct pe main

Pentru că atunci orice lucru neterminat al oricui blochează pe toată lumea. Cu ramuri, main e întotdeauna o versiune care funcționează, iar ce e în lucru stă deoparte până e gata.

15 · În echipă

Pull request și conflicte

Pull request-ul nu e o formalitate birocratică. E momentul în care altcineva se uită la ce ai scris înainte ca asta să devină parte din proiect. La un proiect de echipă de patru oameni, e singura ocazie în care ceilalți trei află ce ai făcut.

PasulUnde
lucrezi pe ramura ta, faci commit-urila tine
git push -u origin ramura-meala tine
deschizi un pull requestpe GitHub
un coleg citește și comenteazăpe GitHub
se îmbină în mainpe GitHub
git switch main și git pullla tine

Conflictele nu sunt o avarie

Sunt felul în care Git spune că nu poate decide în locul tău. Sus e ce ai tu, jos e ce vine.

Rezolvă tuRezolvă-l

Care obicei previne cele mai multe conflicte?

git pull la început de zi.

16 · În echipă

Patru reguli, pentru semestrul ăsta

  1. git pull înainte să începi, de fiecare dată
  2. o ramură pentru fiecare lucru; main merge întotdeauna
  3. mesaje de commit care spun ce s-a schimbat
  4. niciun secret și niciun fișier uriaș în depozit
Cine ce face

Scrieți în README.md cine răspunde de ce: colectare, curățare, analiză, raport. Nu ca să vă împărțiți vina, ci ca să știe fiecare pe cine întreabă.

17 · Cadrul teoretic

Încadrarea teoretică

Datele nu produc întrebări. Teoria produce întrebări, iar datele răspund la ele sau refuză.

Fără un cadru, un proiect de analiză devine o colecție de grafice despre care nimeni nu poate spune dacă sunt importante.

De unde vine o întrebare de cercetare?

Din literatură. Datele spun la ce întrebări poți răspunde; literatura spune care întrebări merită puse. Un proiect care pornește de la „ce pot calcula” ajunge la rezultate corecte și fără sens.

18 · Cadrul teoretic

Un exemplu lucrat: tranzițiile energetice

Exemplul e dintr-o cercetare adevărată, și merită urmărit pas cu pas pentru că arată forma pe care trebuie s-o aibă și proiectul vostru.

Punctul de plecare e literatura: mai mulți autori, care studiază tranzițiile energetice și economia energiei, ajung la aceeași structură în trei dimensiuni. Nu e o alegere a cercetătorului, e ce spune domeniul.

PilonDate și sursăRol teoretic
EconomieWDI: PIB/locuitor, populație, urbanizarePeisajul: capacitatea de a investi și cererea de energie. Explică diferențele dintre țări și intră în regresii.
InstituțiiWGI: Government EffectivenessModelul de guvernanță: capacitatea de a pune în practică. Explică variația dintre țări aflate la același nivel economic.
Sistem energeticEIA: cărbune, eolian, solar, hidro, nuclear, CO₂Regimul și nișele: structura energetică, blocajele moștenite, creșterea regenerabilelor. Baza clusterizării.

Abia după ce există tabelul ăsta se pot scrie întrebările, și fiecare întrebare atinge cel puțin doi piloni:

  1. Economia și tranziția: țările cu PIB pe locuitor mai mare reduc mai repede ponderea cărbunelui și cresc ponderea regenerabilelor?
  2. Instituțiile: țările cu un nivel mai ridicat al eficienței guvernamentale au o creștere mai rapidă a energiei eoliene și solare?
  3. Regimurile energetice: ce tipuri de sisteme energetice se disting între țări, pe baza mixului de electricitate și a emisiilor?
Ce se vede în tabelul ăla

Fiecare rând leagă trei lucruri: un concept, o sursă de date concretă, și rolul pe care îl joacă în argument. Dacă unul dintre cele trei lipsește, pilonul nu ține: un concept fără date nu se poate testa, iar date fără rol teoretic sunt doar coloane.

Ce face ca cele trei întrebări să fie întrebări de cercetare?

Ies dintr-un cadru și se pot infirma.
