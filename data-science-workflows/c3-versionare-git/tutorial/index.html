02 · Ce face Git

Ce face Git

În absența unui sistem de versionare, evoluția unui proiect se reconstituie din copii succesive ale acelorași fișiere, cu denumiri improvizate și fără o evidență a diferențelor dintre ele. Git înlocuiește această practică printr-un istoric structurat: fiecare modificare este înregistrată, atribuită unui autor și datată, iar orice stare anterioară poate fi refăcută.

  1. 01
    Înregistrează fiecare schimbareistoric

    Nu doar ultima versiune, ci toate, cu autorul și data fiecărei schimbări.

  2. 02
    Permite revenireareveniri

    La orice versiune anterioară, fără pierderea stării curente.

  3. 03
    Permite lucrul în paralelcolaborare

    Mai multe persoane lucrează pe aceleași fișiere, iar Git îmbină apoi modificările.

  4. 04
    Păstrează totul în dosarul proiectuluiun singur loc

    Întreaga istorie se află în subdosarul .git, nu într-un serviciu extern.

  5. 05
    Izolează experimenteleramuri

    Modificările experimentale se fac pe o ramură separată, iar codul principal rămâne neatins.

  6. 06
    Funcționează localfără internet

    Git nu necesită conexiune la internet. GitHub este doar locul de sincronizare.

O distincție esențială

Git și GitHub nu sunt același lucru. Git este programul instalat local, care păstrează istoria. GitHub este o platformă care găzduiește copii ale acestei istorii. Git poate fi folosit fără GitHub; invers, nu.

03 · Ce face Git

Git și GitHub

Git și GitHub sunt adesea confundate, dar îndeplinesc funcții diferite. Git este programul care păstrează istoricul pe calculatorul fiecărui membru; GitHub este serviciul care găzduiește o copie a acestui istoric și o face accesibilă echipei.

Gitprogram instalat pe calculator
  • păstrează istoricul proiectului
  • funcționează fără internet
  • se folosește din terminal
GitHubplatformă online
  • găzduiește depozitele, ca o copie independentă de calculator
  • spațiul comun al echipei, fără arhive trimise prin email
  • arată cine ce a făcut și când
Evaluarea proiectului

Proiectul se evaluează pe baza depozitului: nu doar rezultatul final, ci întregul parcurs (ce s-a încercat, ce s-a abandonat, cine a contribuit). Un depozit cu un singur commit în ziua predării nu documentează acest parcurs.

Depozitul (repository)

Un depozit (repository, pe scurt repo) este un dosar obișnuit în care Git a creat un subdosar ascuns, .git. Acolo se păstrează întreaga istorie.

LocalRemote

La curs, repo-ul de pe GitHub există deja pentru fiecare echipă; copia locală se face la pasul următor, cu git clone.

04 · Ce face Git

Cele trei zone

Comenzile Git se înțeleg cel mai ușor prin modelul celor trei zone: dosarul de lucru, zona de pregătire și istoricul local, la care se adaugă copia de pe GitHub. Fiecare comandă mută o modificare dintr-o zonă în următoarea.

În diagrama de mai jos, săgeata dintre două zone poartă numele comenzii care face trecerea. Terminalul de sub diagramă reproduce răspunsurile lui Git, inclusiv pentru o comandă dată în ordinea greșită: git commit fără nimic în pregătire primește „nothing added to commit”.

Pentru un proiect nou, fără repo pe GitHub

Procedura inversă, de la un dosar local la un depozit pe GitHub, este descrisă în fișa Lucrul cu Git: depozitul se creează local, apoi se leagă de un repo gol de pe GitHub.

git init                          # depozit local, gol
git add .                         # după ce .gitignore este scris
git commit -m "first commit"
git branch -m master main         # ramura principala devine main
git remote add origin <GitHub_URL>
git push -u origin main

Dacă repo-ul de pe GitHub are deja conținut (de exemplu, un README), cele două istorii nu au un punct comun și se unesc o singură dată: git pull origin main --allow-unrelated-histories, apoi git branch -u origin/main.

git init în dosarul greșit

Rulat din greșeală în dosarul personal (home), git init pune sub urmărire întregul lui conținut. Remedierea: ștergerea dosarului .git creat acolo; fișierele nu sunt afectate. În PowerShell, din dosarul respectiv: Remove-Item -Recurse -Force .git.

06 · Depozitul echipei

.gitignore

Un fișier text, aflat în rădăcina proiectului, care enumeră ce nu trebuie urmărit. Datele mici ale proiectului intră în depozit (data/raw, data/processed), ca analiza să poată fi refăcută; în .gitignore se trec mediul virtual, secretele, fișierele temporare ale programelor și fișierele foarte mari, trecute pe nume:

# mediul virtual și fișierele temporare

__pycache__/
.ipynb_checkpoints/

# secretele

# fișierele de peste 50 MB, câte unul; caietul spune de unde se descarcă
data/raw/sci_nuts3.csv

Alte rânduri utile, după nevoie: .vscode/, .DS_Store, Thumbs.db. Fișierul .gitignore intră în depozit ca orice alt fișier.

Un fișier adăugat din greșeală trebuie…Comanda
doar scos din zona de pregătire (rămâne pe disc)git reset -- "nume fisier.ipynb"
scos complet de sub urmărirea Git, dar păstrat în proiectgit rm --cached nume_fisier

Cum se curăță istoricul

Întâi, întotdeauna: parola sau cheia se schimbă imediat. După aceea, chiar dacă istoricul nu se curăță perfect, valoarea veche nu mai deschide nimic.

Commit-ul este doar local (fără push)

Fișierul se scoate din ultimul commit, iar commit-ul se reface:

git rm --cached .env           # scos din Git, rămâne pe disc
echo .env >> .gitignore        # ca să nu mai intre
git add .gitignore
git commit --amend --no-edit   # ultimul commit, rescris fără .env

Commit-ul a ajuns pe GitHub

Fișierul trebuie scos din toate commit-urile: istoricul se rescrie, cu git filter-repo, pe o clonă proaspătă:

pip install git-filter-repo

git clone https://github.com/dsw-ubb-2026/echipa-N.git curatare
cd curatare
git filter-repo --invert-paths --path .env   # .env, scos din tot istoricul

git remote add origin https://github.com/dsw-ubb-2026/echipa-N.git
git push --force --all                       # înlocuiește istoricul de pe GitHub

Dacă parola este un rând într-un fișier care rămâne (de exemplu, un caiet), se înlocuiește doar textul: git filter-repo --replace-text inlocuiri.txt, cu un rând parola_veche==>*** în fișier.

De ce este mai dificil

  • Copiile descărcate rămân. Fiecare coleg care a făcut pull are încă istoricul vechi: își șterge dosarul proiect/ și clonează din nou. Un push din copia veche aduce parola înapoi.
  • Commit-urile primesc coduri noi. Linkurile vechi spre commit-uri nu mai funcționează.
  • GitHub poate păstra o vreme commit-urile vechi, de exemplu în pull request-uri. O ștergere completă se cere prin GitHub Support.
  • Ce a văzut deja cineva nu se mai poate șterge. De aceea schimbarea parolei este pasul care contează.

Prevenirea rămâne cea mai simplă: .env stă în .gitignore înainte de primul commit. Șablonul echipelor îl are deja.

07 · Depozitul echipei

Primul commit

Primul commit al echipei, ca în caietul 03 (secțiunea 7.4), pe main: un membru completează, provizoriu, README.md (titlul, întrebarea de cercetare, unitatea de analiză, tabelul surselor), iar altul adaugă src/date_api.py. Fiecare își publică modificarea pe GitHub, după un git pull. Înainte de primul commit, istoricul local și cel de pe GitHub conțin doar commit-ul din șablon.

Pas cu pasPrimul commit al echipei

Același ciclu se repetă la fiecare pas al proiectului, din caietul pasului (pe dev, de la slide-ul următor):

# unde sunt, ce s-a schimbat?
git status

# ce intra in acest commit
git add notebooks/01_collection.ipynb

# il scriu in istoric, cu un mesaj care spune ceva
git commit -m "Pregatim tabelele regionale si migratia"

# intai ce au trimis colegii, apoi trimit si eu
git pull
git push
Frecvența commit-urilor

Un commit nu este o livrare, ci un punct de revenire. Regula practică: câte un commit pentru fiecare unitate de lucru încheiată care poate fi descrisă printr-un mesaj scurt.

Înainte de primul commit: identitatea autorului

Fiecare commit conține un nume și o adresă de email. Git nu verifică datele: folosește exact valorile configurate, o singură dată pe calculator. Cu o adresă diferită de cea a contului de GitHub, commit-urile apar pe GitHub fără legătură cu vreun cont; verificarea se face la finalul lecției, pe pagina commit-ului.

08 · În echipă

Ramurile: main și dev

O ramură este o linie de lucru paralelă. Echipa folosește două: main, versiunea stabilă, cea care se predă, și dev, pe care se lucrează zilnic. Ce se face pe dev nu afectează main până la îmbinare. În diagramă, comenzile se aplică în ordine, de la stânga la dreapta; lângă graf, dosarul arată ce fișiere există pe ramura curentă.

Exercițiumain și dev
Cine, cândComandaCe face
un membru, o datăgit switch -c devcreează dev din main și trece pe ea
același membrugit push -u origin devpublică dev pe GitHub și o leagă de origin/dev
ceilalți, o datăgit fetch ; git switch devaduc dev de pe GitHub și trec pe ea
oricinegit branchlistează ramurile; cea curentă are *
la o sarcină încheiatăgit switch main ; git pulltrece pe main, la zi cu GitHub

oricândgit log --oneline --graph --allacelași graf, desenat în terminal
De ce nu se lucrează direct pe main

Pentru că orice modificare neterminată ar afecta întreaga echipă. Cu dev, main rămâne permanent o versiune care rulează, iar lucrul în desfășurare stă separat până la final.

09 · În echipă

Pull, apoi push

Pe dev lucrează toată echipa, deci GitHub primește commit-uri de la mai mulți membri. Diagrama reconstituie situația în care doi membri lucrează simultan: fiecare coloană este istoricul unui depozit, cu cel mai nou commit sus. Push-ul celui care a rămas în urmă este refuzat până aduce, cu git pull, ce îi lipsește.

Pas cu pasDoi colegi și GitHub, pe dev

Conținutul din dev se integrează în main după fiecare sarcină importantă încheiată (curățarea datelor, setul de vizualizări, modelul): nu la fiecare commit, dar nici doar la final. Integrarea este îmbinarea de la slide-ul despre ramuri: git switch main, git merge dev, git push.

Tot fluxul, pe un singur tabel (și în fișa Lucrul cu Git):

Cine, cândComandaApoi
o dată, un membru al echipeigit switch -c devgit push -u origin dev
o dată, ceilalțigit fetchgit switch dev
zilnic, fiecaregit switch devgit pull
la fiecare commitgit add . ; git commit -m "..."git pull ; git push
după o sarcină importantăgit switch main ; git pullgit merge dev ; git push
Fișiere separate

Fiecare pas are caietul lui și un responsabil (notebooks/01_collection.ipynb, notebooks/02_preprocessing.ipynb); la un caiet se lucrează pe rând, iar încercările stau în caiete separate. Codul comun stă în src/. Conflictele apar doar când două persoane modifică aceleași rânduri.

Ce face git merge dev

Integrează în main toate commit-urile care există în dev, dar nu și în main. Dacă main nu a primit commit-uri noi între timp, eticheta main doar avansează (fast-forward).

10 · În echipă

Conflictele

Un conflict apare la git pull (sau la git merge) când două persoane au modificat același rând. Git nu poate alege între variante: le pune pe amândouă în fișier, între marcaje, iar alegerea o face echipa. Conflictele apar mai ales în fișierele comune, din src/; la caietele pașilor se lucrează pe rând.

ExercițiuRezolvarea conflictului
În fișierCe înseamnă
<<<<<<< HEADîncepe varianta de pe calculator
=======desparte cele două variante
>>>>>>> 3c1f2e9se termină varianta adusă de pe GitHub (commit-ul colegului)

După rezolvare, marcajele nu mai există, iar pașii sunt cei obișnuiți: git add, git commit -m "rezolvat conflict", git push.

Pull request

Pe GitHub, integrarea lui dev în main se poate face și printr-un pull request: se solicită îmbinarea, iar un coleg o revizuiește înainte. Pentru proiectul echipei este suficient git merge dev din terminal; pull request-ul este util când echipa dorește o revizuire prealabilă a codului.

13 · Verificarea

Citirea lui git status

git status este comanda folosită cel mai des: se rulează înainte de fiecare add și înainte de fiecare commit. Ieșirea are trei grupuri, fiecare corespunzând unei zone: ce intră în commit (verde), ce s-a modificat, dar nu a trecut prin git add, și fișierele noi, pe care Git nu le urmărește încă (roșu). În terminalul real, fiecare grup are dedesubt și o indicație între paranteze, de exemplu (use "git add <file>..." to update what will be committed).

ExercițiuCe intră în commit
În git statusZonaIntră în commit?
Changes to be committedpregătireda
Changes not staged for commitdosar, fișier urmărit și modificatnu, până la git add
Untracked filesdosar, fișier nounu, până la git add

Varianta scurtă, git status --short, pune aceleași informații pe două coloane: prima pentru pregătire, a doua pentru dosar. M înseamnă modificat și pregătit, M modificat, dar nepregătit, iar ?? fișier neurmărit.

Încadrarea teoretică

Datele nu generează întrebări. Întrebările provin din teorie, iar datele pot susține sau infirma răspunsurile propuse. Fără un cadru, un proiect devine o colecție de grafice a căror relevanță nu poate fi evaluată.

În fluxul de lucru, literatura intervine în patru moduri, fiecare răspunzând la altă întrebare. Teoria vine prima, la definirea întrebării. Metoda intervine la analiză: dacă alte studii au abordat deja o întrebare asemănătoare, analiza pornește de la modelul lor, nu de la zero. Documentația se consultă la fiecare pas de cod, iar descrierea datelor se citează oriunde acestea sunt folosite.

16 · Cadrul teoretic

Cadrul proiectului: ce explică legăturile dintre locuri

Un cadru teoretic spune ce trebuie explicat, prin ce și de ce. În proiectul cursului, de explicat este legătura dintre două locuri, măsurată prin SCI. Patru factori o pot explica, fiecare cu mecanismul lui și cu variabila care îl măsoară. Ce nu explică niciunul este reziduul: legăturile mai puternice sau mai slabe decât prezic factorii. Din el pornesc întrebările echipelor.

Literatura de la temelia cadrului este cea despre sistemele migratorii: locurile legate prin migrație rămân legate și prin fluxuri de informație, bani și vizite, iar rețelele de migranți facilitează migrația celor care urmează. SCI permite observarea directă a unei părți din aceste legături. Distanța și migrația intră în modelul din C7; istoria și locurile nu au încă o variabilă gata făcută, deci echipa care le alege își construiește măsura.

Întrebările derivate din cadru

  1. Migrația: sunt perechile de țări cu mai mulți migranți la mie mai puternic conectate, la aceeași distanță?
  2. Istoria: generează granițele istorice și minoritățile (de exemplu, în cazul României și al Ungariei) legături pe care migrația recentă nu le explică?
  3. Ce rămâne: unde sunt legăturile mai puternice decât prezic distanța și migrația împreună și ce au în comun aceste locuri?
Contribuția echipelor

Fiecare echipă alege un factor și un loc: un coridor (de exemplu, România și Italia) sau o țară analizată la nivel regional. Se poate adăuga un factor nou, de exemplu limba sau religia, cu condiția să poată fi măsurat.

Teoriamecanismele care explică fenomenul, conceptele și ipotezele care decurg din ele

  • Palloni și colegii (2001)teoria rețelelor de migranți: legăturile cu cei plecați anterior reduc costurile și riscurile migrației pentru cei care urmează. De aici ideea că migrația și legăturile sociale sunt asociate.
  • de Haas (2010)migrația și legăturile se întrețin reciproc (mecanisme de feedback), dar nu nelimitat. De aici regula proiectului: relația dintre SCI și migrație acționează în ambele sensuri, deci nu se poate afirma care dintre ele o produce pe cealaltă.
  • Sandu (2005)migrația românească nu este uniformă: localitățile se organizează în câmpuri de migrație, fiecare cu destinațiile lui (între altele Germania, Ungaria, Italia, Turcia, Spania). Oferă cadrul românesc al întrebării de cercetare.
  • Sandu (2025)județele României și cele șase destinații mari (Italia, Spania, Germania, Regatul Unit, Franța, Austria), pe fluxuri 2011-2021. Reperul cu care se compară orice hartă a diasporei construită din SCI.

Indicatorii regionali, într-un tabel

Denumirile regiunilor provin din nomenclatorul GISCO, pe care caietul îl citește direct de la adresa lui, cu pd.read_csv; lungimea codului indică nivelul: 2 caractere țara, 4 regiunea, 5 județul. Indicatorii (populația, densitatea, PIB-ul pe locuitor, vârsta medie, studiile superioare, șomajul și participarea la rețele sociale) se cer direct de la Eurostat, pe regiuni NUTS 2, cu funcția din src/date_api.py: o listă spune ce se cere, iar o buclă face cererile și pune tabelele unul sub altul.

Pas cu pasIndicatorii într-un singur tabel
De ce format lung, nu lat

Un rând pentru fiecare combinație de regiune și indicator. Astfel, un indicator nou se adaugă fără coloane noi, iar valorile lipsă se numără direct. În C4, tabelul se transformă în format lat, cu un rând pe regiune.

Același pas se aplică și datelor SCI: coloanele cu nume în engleză sunt redenumite după semnificația lor în proiect (user_region devine regiune_1, scaled_sci devine sci). La NUTS 2, tabelul are 298 × 298 = 88.804 rânduri: fiecare regiune cu fiecare, inclusiv cu ea însăși, iar fiecare pereche apare în ambele ordini.

Migrația: țări și grupuri de țări

Fișierul migrației vine din caietul 02; caietul 03 îl citește din depozitul cursului, de la adresa DATE_C2. Înainte de orice analiză, aceleași patru operații, de fiecare dată.

Exercițiu de codExplorare inițială

Eurostat raportează în aceeași coloană țări și grupuri de țări (Uniunea, toți străinii, cetățenii proprii), iar grupurile trebuie scoase: altfel aceiași oameni sunt numărați de mai multe ori. Caietul păstrează doar codurile de două litere și scoate rândurile în care cetățenia coincide cu țara de rezidență.

Scopul explorării inițiale

Scopul nu sunt rezultatele, ci semnele că datele nu corespund așteptărilor: un număr de rânduri diferit de cel estimat, o coloană text care ar trebui să fie numerică, valori lipsă neașteptate. Analiza propriu-zisă începe la cursul 6; acum se verifică doar că datele pot fi analizate.
