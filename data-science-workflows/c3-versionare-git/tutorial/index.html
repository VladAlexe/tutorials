Versionare și colaborare cu Git

Același drum ca la curs, explicat pe larg și cu aceleași exerciții. Dacă le-ai făcut la clasă, apar deja rezolvate; dacă vrei să le reiei, îți poți reseta progresul din contul tău.

01 · Cursul

Versionare și colaborare cu Git

Ora de azi are două jumătăți care par fără legătură, dar nu sunt. În prima învățăm Git, adică felul în care un proiect își ține minte propria istorie. În a doua punem întrebarea de cercetare a proiectului vostru.

Legătura dintre ele e asta: un proiect de analiză nu e o grămadă de fișiere, e un drum. Git păstrează drumul, iar cadrul teoretic spune încotro duce. Fără primul, nu poți arăta cum ai ajuns; fără al doilea, nu poți spune de ce ai pornit.

03 · Ce face Git

Ce face Git

Un sistem de versionare rezolvă o problemă pe care toată lumea a avut-o înainte să știe că are un nume: fișiere numite analiza_final_v2_FINAL_bun.py, și nimeni care să-și amintească ce era diferit în v1.

ExploratorȘase lucruri
Distincția care se uită cel mai des

Git și GitHub nu sunt același lucru. Git e programul de pe calculatorul tău, care ține istoria. GitHub e un site care găzduiește copii ale acelei istorii. Poți folosi Git fără GitHub toată viața; invers, nu.

07 · Primii pași

Credențiale

Git scrie în fiecare commit cine l-a făcut. Nu verifică nimic: scrie ce i-ai spus. De aceea, dacă pui o adresă greșită, commit-urile tale apar pe GitHub ca ale nimănui.

08 · Primii pași

Ciclul de lucru

În practică, o zi de lucru arată așa:

# unde sunt?
git status

# aleg ce intra in commit-ul asta
git add colectare/migratie.py

# il scriu in istoric, cu un mesaj care spune ceva
git commit -m "colectare migratie, Eurostat migr_pop1ctz"

# il trimit colegilor
git push
Rulează pas cu pasPrimul commit, pas cu pas
Cât de des faci commit

Mai des decât crezi. Un commit nu e o livrare, e un punct la care te poți întoarce. Regula practică: de fiecare dată când ai terminat un lucru care are un nume.

10 · GitHub

GitHub

  • o platformă online care găzduiește depozite Git
  • un loc unde proiectul există și dacă laptopul nu mai există
  • locul unde echipa se întâlnește, fără să-și trimită arhive pe mail
  • un portofoliu: se vede cine ce a făcut, și când
Pentru voi, concret

Nota de la proiect se dă pe ce se vede în depozit. Nu pe fișierul final, ci pe drum: ce ați încercat, ce ați aruncat, cine a lucrat. Un depozit cu un singur commit în ziua predării spune o poveste, și nu una bună.

11 · GitHub

Două feluri de a începe

Ca în fișa „Lucrul cu Git” de la curs, sunt două variante, după cum există sau nu deja depozitul pe GitHub.

Varianta 1: git init

Doar dacă nu există încă depozit pe GitHub.

git init                          # depozit local, gol
git add .                         # fisierele existente
git commit -m "first commit"
git branch -m master main         # ramura principala devine main
git remote add origin <GitHub_URL>
git push -u origin main

Varianta 2: git clone, cea de la curs

Când depozitul echipei există deja pe GitHub.

git clone https://github.com/DSW2026-ORG/TeamX.git Proiect
cd Proiect
git status
git branch -vv            # main urmareste origin/main

Caz special

Ai făcut local git init, dar depozitul de pe GitHub există deja și are conținut (de exemplu un README). Istoriile nu au legătură, deci le unești o dată:

git remote add origin <GitHub_URL>
git pull origin main --allow-unrelated-histories
git branch -u origin/main

git branch -rramurile de pe GitHub (origin/...)
git branch -atoate
git branch -vvfiecare ramură și pe cine urmărește (upstream)
git remote -vadresa lui origin

13 · În echipă

Ramuri

O ramură e o linie de lucru paralelă. Pe ea strici ce vrei, iar main rămâne întreg și gata de predat oricând.

Desenează tuDesenează-l tu
ComandaCe face
git branchce ramuri există și pe care ești
git switch -c curatarefaci una nouă și treci pe ea
git switch mainte întorci
git merge curatareaduci în main ce ai făcut pe ea
De ce nu lucrează toți direct pe main

Pentru că atunci orice lucru neterminat al oricui blochează pe toată lumea. Cu ramuri, main e întotdeauna o versiune care funcționează, iar ce e în lucru stă deoparte până e gata.

14 · În echipă

Fluxul echipei: main și dev

Fluxul din fișa „Lucrul cu Git” are două ramuri. main e versiunea care merge și care se predă. dev e ramura pe care lucrează toată echipa zi de zi. Ce e pe dev ajunge în main după fiecare task important terminat: curățarea datelor, setul de vizualizări, modelul. Nu la fiecare commit, și nu doar la final.

Pas cu pasCe se întâmplă cu commit-urile
Cine, cândComandaApoi
o dată, unul din echipăgit switch -c devgit push -u origin dev
o dată, ceilalțigit fetchgit switch dev
zilnic, fiecaregit switch devgit pull
când salvezigit add . ; git commit -m "..."git pull ; git push
după un task importantgit switch main ; git pullgit merge dev ; git push
Fișiere separate

Lucrați, pe cât se poate, în fișiere separate (de exemplu analiza_vlad.ipynb, analiza_maria.ipynb). Conflictele apar doar când doi oameni schimbă aceleași rânduri.

Ce face git merge dev

Ia toate commit-urile care există în dev, dar nu încă în main, și le aduce în main. Dacă main n-a primit nimic între timp, eticheta main doar avansează (fast-forward).

15 · În echipă

Conflictele

Un conflict apare la git pull (sau la git merge) când tu și un coleg ați schimbat aceleași rânduri. După rezolvare: git add ., git commit -m "rezolvat conflict", git push.

Pull request

Pe GitHub, aducerea lui dev în main se poate face și printr-un pull request: ceri îmbinarea, iar un coleg se uită întâi peste ea. Pentru proiectul nostru ajunge git merge dev din terminal; pull request-ul e un pas în plus, util când echipa vrea să citească înainte.

Conflictele nu sunt o avarie

Sunt felul în care Git spune că nu poate decide în locul tău. Sus e ce ai tu, jos e ce vine.

17 · Cadrul teoretic

Încadrarea teoretică

Datele nu produc întrebări. Teoria produce întrebări, iar datele răspund la ele sau refuză. Fără un cadru, un proiect devine o colecție de grafice despre care nimeni nu poate spune dacă sunt importante.

În fluxul de lucru, literatura apare de patru ori, și fiecare fel răspunde la altă întrebare. Teoria vine prima, la definirea întrebării. Metoda vine la analiză: dacă alții au răspuns deja la o întrebare asemănătoare, pornești de la modelul lor, nu de la zero. Documentația o deschizi la fiecare pas de cod. Iar descrierea datelor o citezi oriunde le folosești.

19 · Cadrul teoretic

Cadrul nostru: legături și migrație

Un cadru are forma unui templu: întrebarea sus, conceptele cu datele lor ca piloni, literatura ca temelie. Temelia e literatura despre sistemele migratorii: locurile legate prin migrație rămân legate și prin informație, bani și vizite, iar rețelele de migranți fac drumul mai ușor pentru cei care vin după. Indicele SCI ne lasă să vedem o parte din legăturile astea, măsurate direct.

Întrebările care ies din cadru

  1. Migrația: perechile de țări cu mai mulți migranți sunt mai legate, la aceeași distanță?
  2. Istoria: granițele vechi și minoritățile, cum e cazul României cu Ungaria, dau legături pe care migrația recentă nu le explică?
  3. Ce rămâne: unde sunt legăturile mai puternice decât prezic distanța și migrația împreună, și ce au în comun locurile acelea?
Unde intrați voi

Fiecare echipă alege un colț din templu: un coridor, de exemplu România și Italia, sau o țară privită pe regiuni. Puteți adăuga un pilon, de exemplu limba sau religia, dacă îl puteți măsura.

22 · Datele

Regiunile, într-un tabel

Fiecare fișier din C2 are câte un rând pe regiune, cu un cod NUTS. Numele regiunilor vin din nomenclatorul Eurostat GISCO, iar lungimea codului spune nivelul: 2 caractere țara, 4 regiunea, 5 județul.

Rulează pas cu pasNomenclatorul și tabelul regional

Același pas se face și pentru SCI: coloanele în engleză primesc nume care spun ce înseamnă în proiect (user_region devine regiune_1, scaled_sci devine sci). Sunt 88.804 de rânduri la NUTS 2 și 1.803.649 la NUTS 3.
