01 · Cursul

Versionare și colaborare cu Git

Lecția de azi are două părți, aparent fără legătură. Prima tratează Git, adică mecanismul prin care un proiect își păstrează propria istorie. A doua este dedicată formulării întrebării de cercetare a proiectului.

Legătura dintre ele: un proiect de analiză nu este o colecție de fișiere, ci un parcurs. Git documentează parcursul, iar cadrul teoretic îi stabilește direcția. Fără primul, rezultatul nu poate fi reconstituit; fără al doilea, nu poate fi justificat.

03 · Ce face Git

Ce face Git

Un sistem de versionare rezolvă o problemă frecventă: fișiere numite analiza_final_v2_FINAL_bun.py, fără nicio evidență a diferențelor față de v1.

  1. 01
    Înregistrează fiecare schimbareistoric

    Nu doar ultima versiune, ci toate, cu autorul și data fiecărei schimbări.

  2. 02
    Permite revenireareveniri

    La orice versiune anterioară, fără pierderea stării curente.

  3. 03
    Permite lucrul în paralelcolaborare

    Mai multe persoane lucrează pe aceleași fișiere, iar Git îmbină apoi modificările.

  4. 04
    Păstrează totul în dosarul proiectuluiun singur loc

    Întreaga istorie se află în subdosarul .git, nu într-un serviciu extern.

  5. 05
    Izolează experimenteleramuri

    Modificările experimentale se fac pe o ramură separată, iar codul principal rămâne neatins.

  6. 06
    Funcționează localfără internet

    Git nu necesită conexiune la internet. GitHub este doar locul de sincronizare.

O distincție esențială

Git și GitHub nu sunt același lucru. Git este programul instalat local, care păstrează istoria. GitHub este o platformă care găzduiește copii ale acestei istorii. Git poate fi folosit fără GitHub; invers, nu.

O eroare frecventă

Rulat din greșeală în dosarul personal (home), git init pune sub urmărire întregul conținut al acestuia. Remedierea constă în ștergerea dosarului .git creat acolo; fișierele nu sunt afectate. În PowerShell, din dosarul respectiv: Remove-Item -Recurse -Force .git.

08 · Primii pași

Credențiale

Git înregistrează în fiecare commit autorul acestuia. Nu verifică datele: folosește exact valorile configurate. De aceea, cu o adresă greșită, commit-urile apar pe GitHub fără legătură cu vreun cont.

09 · Primii pași

Ciclul de lucru

În practică, ciclul obișnuit de lucru este următorul:

# unde sunt?

# il scriu in istoric, cu un mesaj care spune ceva
git commit -m "colectare migratie, Eurostat migr_pop1ctz"

# il trimit colegilor

Pas cu pasPrimul commit, pas cu pas
Frecvența commit-urilor

Un commit nu este o livrare, ci un punct de revenire. Regula practică: câte un commit pentru fiecare unitate de lucru încheiată care poate fi descrisă printr-un mesaj scurt.

13 · GitHub

GitHub

  • o platformă online care găzduiește depozite Git
  • o copie a proiectului, independentă de calculatorul local
  • spațiul comun al echipei, fără arhive trimise prin email
  • un portofoliu: arată cine ce a făcut și când
Evaluarea proiectului

Proiectul se evaluează pe baza depozitului: nu doar rezultatul final, ci întregul parcurs (ce s-a încercat, ce s-a abandonat, cine a contribuit). Un depozit cu un singur commit în ziua predării nu documentează acest parcurs.

14 · GitHub

Două feluri de a începe

Ca în fișa „Lucrul cu Git” de la curs, există două variante, în funcție de existența depozitului pe GitHub.

Varianta 1: git init

Se folosește doar dacă depozitul nu există încă pe GitHub.

git init                          # depozit local, gol
git add .                         # fisierele existente
git commit -m "first commit"
git branch -m master main         # ramura principala devine main
git remote add origin <GitHub_URL>
git push -u origin main

Varianta 2: git clone, cea de la curs

Se folosește când depozitul echipei există deja pe GitHub.

git clone https://github.com/dsw-ubb-2026/depozitul-echipei.git proiect
cd proiect
git status
git branch -vv            # main urmareste origin/main

Caz special

Depozitul local a fost creat cu git init, dar depozitul de pe GitHub există deja și are conținut (de exemplu, un README). Cele două istorii nu au un punct comun, deci se unesc o singură dată:

git remote add origin <GitHub_URL>
git pull origin main --allow-unrelated-histories
git branch -u origin/main
VerificareCe afișează
git branchramurile locale
git branch -rramurile de pe GitHub (origin/...)
git branch -atoate ramurile
git branch -vvfiecare ramură și pe cine urmărește (upstream)
git remote -vadresa lui origin

17 · În echipă

Ramuri

O ramură este o linie de lucru paralelă. Modificările de pe ea nu afectează main, care rămâne funcțional și gata de predare în orice moment.

ExercițiuGraful ramurilor
ComandaCe face
git branchlistează ramurile și o marchează pe cea curentă
git switch -c curatarecreează o ramură nouă și trece pe ea
git switch mainrevine pe main
git merge curatareintegrează în main modificările de pe ramură
De ce nu se lucrează direct pe main

Pentru că orice modificare neterminată ar afecta întreaga echipă. Cu ramuri, main rămâne permanent o versiune funcțională, iar lucrul în desfășurare este izolat până la finalizare.

18 · În echipă

Fluxul echipei: main și dev

Fluxul din fișa „Lucrul cu Git” folosește două ramuri. main este versiunea funcțională, cea care se predă. dev este ramura pe care lucrează zilnic întreaga echipă. Conținutul din dev se integrează în main după fiecare sarcină importantă încheiată (curățarea datelor, setul de vizualizări, modelul): nu la fiecare commit, dar nici doar la final.

Pas cu pasCe se întâmplă cu commit-urile
Cine, cândComandaApoi
o dată, un membru al echipeigit switch -c devgit push -u origin dev
o dată, ceilalțigit fetchgit switch dev
zilnic, fiecaregit switch devgit pull
la fiecare commitgit add . ; git commit -m "..."git pull ; git push
după o sarcină importantăgit switch main ; git pullgit merge dev ; git push
Fișiere separate

Pe cât posibil, fiecare membru lucrează în fișiere separate (de exemplu analiza_vlad.ipynb, analiza_maria.ipynb). Conflictele apar doar când două persoane modifică aceleași rânduri.

Ce face git merge dev

Integrează în main toate commit-urile care există în dev, dar nu și în main. Dacă main nu a primit commit-uri noi între timp, eticheta main doar avansează (fast-forward).

19 · În echipă

Conflictele

Un conflict apare la git pull (sau la git merge) când două persoane au modificat aceleași rânduri. După rezolvare: git add ., git commit -m "rezolvat conflict", git push.

Pull request

Pe GitHub, integrarea lui dev în main se poate face și printr-un pull request: se solicită îmbinarea, iar un coleg o revizuiește înainte. Pentru proiectul echipei este suficient git merge dev din terminal; pull request-ul este un pas suplimentar, util când echipa dorește o revizuire prealabilă a codului.

Conflictele nu sunt erori

Prin conflict, Git semnalează că nu poate decide automat între două modificări. În fișier, varianta locală apare deasupra, iar cea preluată, dedesubt.

21 · Cadrul teoretic

Încadrarea teoretică

Datele nu generează întrebări. Întrebările provin din teorie, iar datele pot susține sau infirma răspunsurile propuse. Fără un cadru, un proiect devine o colecție de grafice a căror relevanță nu poate fi evaluată.

În fluxul de lucru, literatura intervine în patru moduri, fiecare răspunzând la altă întrebare. Teoria vine prima, la definirea întrebării. Metoda intervine la analiză: dacă alte studii au abordat deja o întrebare asemănătoare, analiza pornește de la modelul lor, nu de la zero. Documentația se consultă la fiecare pas de cod, iar descrierea datelor se citează oriunde acestea sunt folosite.

24 · Cadrul teoretic

Cadrul proiectului: legături și migrație

Un cadru teoretic poate fi reprezentat ca un templu: întrebarea deasupra, conceptele cu datele lor ca piloni, literatura ca temelie. Temelia este literatura despre sistemele migratorii: locurile legate prin migrație rămân legate și prin fluxuri de informație, bani și vizite, iar rețelele de migranți facilitează migrația celor care urmează. Indicele SCI permite observarea directă a unei părți din aceste legături.

Întrebările derivate din cadru

  1. Migrația: sunt perechile de țări cu mai mulți migranți mai puternic conectate, la aceeași distanță?
  2. Istoria: generează granițele istorice și minoritățile (de exemplu, în cazul României și al Ungariei) legături pe care migrația recentă nu le explică?
  3. Ce rămâne: unde sunt legăturile mai puternice decât prezic distanța și migrația împreună și ce au în comun aceste locuri?
Contribuția echipelor

Fiecare echipă alege o parte a cadrului: un coridor (de exemplu, România și Italia) sau o țară analizată la nivel regional. Se poate adăuga un pilon nou, de exemplu limba sau religia, cu condiția să poată fi măsurat.

29 · Datele

Regiunile, într-un tabel

Fiecare fișier din C2 are câte un rând pe regiune, cu un cod NUTS. Denumirile regiunilor provin din nomenclatorul Eurostat GISCO, iar lungimea codului indică nivelul: 2 caractere țara, 4 regiunea, 5 județul.

Pas cu pasNomenclatorul și tabelul regional
De ce format lung, nu lat

Un rând pentru fiecare combinație de regiune, indicator și nivel. Astfel, un indicator nou se adaugă fără coloane noi, iar valorile lipsă se numără direct. În C4, tabelul se transformă în format lat, cu un rând pe regiune.

Același pas se aplică și datelor SCI: coloanele cu nume în engleză sunt redenumite după semnificația lor în proiect (user_region devine regiune_1, scaled_sci devine sci). Tabelele au 88.804 rânduri la NUTS 2 și 1.803.649 la NUTS 3.
