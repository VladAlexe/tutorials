EchoChamber — arhitectura și povestea aplicației

Două lucruri într-o singură pagină. Întâi, cum funcționează aplicația end-to-end: structura repo-ului, pipeline-ul de date, cum se compun modulele ca niște building blocks, cele 6 tab-uri Gradio. Apoi povestea: cum fiecare săptămână de curs a adăugat fizic o piesă, iar la final toate se conectează într-un sistem coerent.

echochamber-app/ 7 cursuri → 1 aplicație 12 diagrame ~40 min

Aplicația livrabilă (app/app.py) este un strat subțire Gradio peste modulele core/ construite în cursurile C2–C7. Nu rescrie nimic — le compune. Partea III leagă explicit fiecare bucată de cursul ei.

Partea I · Arhitectura

Cum funcționează aplicația, vizual

De la API-ul YouTube la răspunsul afișat în Gradio. Fiecare diagramă arată exact ce intră și ce iese.

01Structura repo-ului

Trei zone: scripts/ + data/ pentru pipeline-ul offline, core/ pentru logica de business, app/ pentru interfață. Albastru = folder, gri = fișier.

echochamber-app/ — structura (fără notebooks)
app/
└─ app.py                     # UI: 6 tab-uri — Setări·Chat·Rezumat·Agent·Toți agenții·Dezbatere

core/                         # logica de business (importată de app)
├─ agent.py                   # un agent: role + retrieval + apel LLM (C6)
├─ graph.py                   # LangGraph: orchestrare multi-agent (C7)
├─ retriever.py               # FAISS retrieval pe vectorstore-ul unui agent (C5)
├─ config.py                  # referință (varianta minimă a app-ului nu îl mai folosește)
└─ metrics.py                 # placeholder

scripts/                      # pipeline CLI: collect → clean → annotate → vectorstore
├─ collect_youtube.py  clean_youtube.py
└─ annotate_axis.py    build_vectorstore.py

assets/
├─ roles/   roles.yaml   # cardurile agenților — sursa pentru app/agent
└─ vectorstores/<slug>/     index.faiss + index.pkl

data/ raw/ cleaned/ annotated/ bubbles/   # pipeline-ul de date
.env  # GEMINI / DEEPSEEK / YOUTUBE keys   requirements.txt

Regula slug-ului. Aceeași valoare (anti_sistem, conspirationist, …) apare în 3 locuri și trebuie identică: cheia din roles.yaml, data/bubbles/<slug>.jsonl, vectorstores/<slug>/. Inconsistent → FileNotFoundError.

02Cele două faze

Sistemul are două faze. Faza A se rulează o singură dată și produce indexurile FAISS. Faza B servește utilizatorul prin Gradio. Singura punte: vectorstore-urile.

Faza A · offline

Pipeline de date

YouTube → colectare → curățare → adnotare → bule → vectorstore. Rulat manual din CLI.

Faza B · runtime

Aplicația Gradio

6 tab-uri. Tab-ul Setări încarcă o știre; restul tab-urilor o folosesc automat ca context.

Puntea unică. Faza A produce assets/vectorstores/<slug>/. Faza B le citește la fiecare cerere prin core/retriever.py. Sunt complet decuplate.

03Pipeline de date offline — file by file

Fiecare script consumă un fișier și produce altul. Dacă pipeline-ul se rupe, te uiți care fișier lipsește între două etape.

04Building blocks — cum se compune app.py

app.py nu e o cutie neagră — se construiește în straturi, ca niște cărămizi. Fundația sunt modulele core/ din C5–C7. Peste ele, fiecare secțiune din fișier adaugă un strat, până la interfața care rulează. Săgețile din stânga arată ce intră în fiecare strat.

Ce blocuri intră în fiecare tab

Fiecare tab e compus din aceleași tipuri de cărămizi, dar combinate diferit. Citește fiecare coloană de jos în sus: input → procesare → backend.

De ce contează. Odată ce vezi cele 5 tipuri de cărămizi (input · stare · _subject · ask_llm · core.agent/graph), oricare tab e doar o combinație de 3–4 dintre ele. Asta face codul ușor de citit și de predat: nu memorezi 6 tab-uri, înveți 5 piese.

05Cele 6 tab-uri — user journey

App-ul are 6 tab-uri. Tab-ul Setări scrie starea partajată (CFG, ART); celelalte o citesc. Fiecare tab e un gr.Interface.

Regula _subject(). Dacă există ȘI o știre încărcată ȘI un subiect scris în tab → subiectul intră peste știre („discută X în contextul acestei știri"). Doar știre → se discută știrea. Doar subiect → se discută subiectul.

06Runtime — un apel din tab-ul Agent

Secvența exactă la un click pe Submit în tab-ul Agent. De sus în jos: fiecare săgeată numerotată = un apel între componente.

Multi-agent-ul nu duplică acest flux. Pașii 2–11 sunt exact ce reutilizează „Toți agenții" în buclă peste roluri și „Dezbatere" prin core.graph.

07Multi-agent debate — LangGraph în core/graph.py

Tab-ul Dezbatere: router_node alege round-robin cine vorbește, fiecare agent_node reutilizează generate_agent_response() din Fig. 5, apoi revine la router.

08Imaginea de ansamblu — offline → runtime

Tot lanțul, de la API extern la răspunsul afișat. Cele două faze sunt separate; singura legătură este linia punctată: vectorstore-urile produse offline, citite de retriever la runtime.

09Dependențe între module — cine importă pe cine

Săgeata = „importă / depinde de". app.py importă direct doar core.agent și core.graph (plus gradio/openai/yaml/requests/bs4). Restul e ascuns în spatele lor.

11Convenții cheie

Slug

Identitatea agentului

Aceeași valoare în 3 locuri: cheia din roles.yaml, data/bubbles/<slug>.jsonl, vectorstores/<slug>/. Inconsistent → FileNotFoundError.

Embedding

Model unic

paraphrase-multilingual-MiniLM-L12-v2, 384 dim, la build ȘI la search. Schimbarea impune rebuild la toate vectorstore-urile.

Provider · Model

Un singur dropdown

Opțiunile sunt "provider|model" (ex. gemini|gemini-2.5-flash). Imposibil ca UI-ul să cuprindă o combinație nepotrivită.

Stare partajată

CFG + ART (modul)

Două dicționare la nivel de modul. Tab-ul Setări scrie, restul citesc. (Alternativa „canonică" Gradio = gr.State; varianta minimă alege simplitatea.)

12Entry points — cum se rulează

comenzi terminal
# Aplicația (Gradio UI · 6 tab-uri)
python -m app.app          # sau:  python app/app.py

# Un singur agent RAG, din terminal
python -m core.agent --agent anti_sistem --text "..." --provider gemini --k 5

# Debate multi-agent
python -m core.graph --agents anti_sistem conspirationist pro_european \
    --text "..." --turns 4 --provider gemini

# Pipeline offline (rulat o singură dată / per refresh date)
python scripts/collect_youtube.py    --handle <canal> --output data/raw/x.jsonl
python scripts/clean_youtube.py      --input data/raw/x.jsonl --output data/cleaned/x.jsonl
python scripts/annotate_axis.py      --input data/cleaned/x.jsonl \
                                     --output data/annotated/x.jsonl --provider gemini
python scripts/build_vectorstore.py

15Viața unui comentariu — povestea unei date

Cel mai clar mod de a vedea cum se leagă cursurile: urmărește un singur comentariu cum se transformă, pas cu pas, până devine o voce discursivă. Fiecare transformare = un curs.

Aici totul se leagă: un comentariu real, scris de cineva pe YouTube, devine — prin 6 transformări, fiecare predată într-o săptămână — o intervenție discursivă a unui agent. Nimic nu e inventat: răspunsul e ancorat în comentarii reale, recuperate semantic, filtrate prin rol.

16Puzzle-ul cursurilor — cum se asamblează în app

Cursurile nu sunt o listă. Sunt piese care se conectează. Săgeți groase = „construiește direct", punctate = „pregătește baza".

18Mesajul cursului final

★ Concluzia

Fiecare curs a adăugat o piesă la sistem. Singur, niciun curs nu produce o aplicație — împreună, formează lanțul:

C3 colectează datele → C4 le adnotează → C5 le indexează →
C6 le folosește pentru a da voce unui agent → C7 pune agenții să discute →
C2 alege modelul → totul devine vizibil în app/app.py

Aplicația nu este un proiect separat. Este suma exactă a celor 7 săptămâni — fiecare bucată trasabilă la cursul ei. Și, ca niște building blocks, fiecare strat se sprijină pe cel de sub el. Asta ai construit.
